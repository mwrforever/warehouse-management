# 报工与开工锁序反转：并发死锁抛未捕获 QueryException → 500

- 发现日期：2026-08-13
- 严重级别：中（运行错误，低概率）
- 状态：已修复（核实确认——生产模块修复波次已统一锁序，本次仅复核标注，无需代码改动）
- 涉及文件：`server/app/Http/Controllers/Api/OperationReportController.php`、`server/app/Http/Controllers/Api/ProductionOrderController.php`

## 问题描述

报工与开工对「工单行 / 工序行」两把锁的获取顺序相反：

- 报工 `store`：**先锁工序行，再锁工单行**（`OperationReportController.php:40,45`）；
- 开工 `start`：**先锁工单行，再锁首工序行**（`ProductionOrderController.php:352-365`）。

并发执行 `start()`（持工单锁等工序锁）与对该首工序的 `report()`（持工序锁等工单锁）时形成等待环，MySQL 会杀一方事务抛 deadlock（error 1213）`QueryException`。`start` 的 catch 只捕获 `ProductionException`（`ProductionOrderController.php:367`），`QueryException` 直接冒泡为 500。

## 证据

```php
// OperationReportController.php:40,45 —— 工序 → 工单
$op = WorkOrderOperation::whereKey($operation->id)->lockForUpdate()->firstOrFail();
...
$order = ProductionOrder::whereKey($op->order_id)->lockForUpdate()->firstOrFail();

// ProductionOrderController.php:352-365 —— 工单 → 首工序
DB::transaction(function () use ($order) {
    $locked = ProductionOrder::whereKey($order->id)->lockForUpdate()->firstOrFail();
    ...
    $first = WorkOrderOperation::where('order_id', $locked->id)
        ->orderBy('seq')->lockForUpdate()->first();
```

## 影响

- 触发概率低（开工与首工序报工同时进行），但一旦触发返回 500 且用户需重试；
- 数据无损（InnoDB 回滚）。

## 建议修复方向

- 统一锁序：`start` 改为先锁首工序行再锁工单行，或 `report` 改为先锁工单行再锁工序行；
- 兜底：`start`/`complete`/`close` 的 catch 增加 `QueryException` 死锁重试或转业务码（如 500 信封 + 重试提示）。

## 处理结论（2026-08-13 复核）

**问题已不存在（此前修复波次已处理），本次复核标注，无需代码改动。** 核实当前代码：

- `ProductionOrderController::start`（:354-380）：**先锁首工序行（`WorkOrderOperation ... orderBy('seq')->lockForUpdate()`，:359-360），后锁工单行（:362）**，与报工同序；
- `OperationReportController::store`（:44-59）：锁序 op → next-op → order；
- 委外回收（OutsourcingController:321-323）：outsourcing → op → order，同段同序；
- 全局锁序约定「op/order 同序、无 order→op 反向路径」已落地，与审查时的证据行号（旧版 :352-365 工单→工序）不符——审查基于的版本已过时。

残留建议（非缺陷，未改）：`start`/`complete` 等 catch 仍只捕 ProductionException；死锁 QueryException 在当前锁序下理论不可达，若未来新增反向锁路径需同步补兜底。
