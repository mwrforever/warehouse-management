### 三、确认问题区

#### B-1.【中】草稿工单被委外草稿单「卡死」：工单 update 重建工序行撞 `outsourcing_orders.operation_id` FK RESTRICT → QueryException 500，且无自愈路径【核验:✅真实】

- 等级：中；分类：① 运行错误（异常路径 500）+ ② 数据丢失类（守卫缺失导致单据不可用）
- 引入：`6df3ab8`（工单 update 引入工序全删重建）与 `488bf3c`（委外表 `operation_id` FK restrict）交叉形成；`b03b989`（PR#32）起 DAG 工单创建即落 `is_outsourced=1` 节点快照（`ProductionOrderController.php:155-165`），使该链路在工单草稿期即可触达。历史清单未报过。
- 证据链（三点合一，均已逐一核实）：
  1. **委外 store 不校验工单状态**：`server/app/Http/Controllers/Api/OutsourcingController.php:107-176` —— 仅校验工序归属（:120-123）、委外标记（:128-130）、节点未完成（:131-133）与 1520 剩余量（:134-139），无任何 `$order->status` 校验；对照同文件 approve 有 `[RELEASED, PRODUCING]` 校验（:358-361）。`git show 03d2ef8` 证实 08-14 的「生产单据校验工单状态」修复波只给 storeReceipt（回收）补了校验、从未覆盖委外 store。路由层仅 `production.outsource.create` 权限（`routes/api.php:309`），无其它门禁。
  2. **工单 update 无委外引用守卫**：`server/app/Http/Controllers/Api/ProductionOrderController.php:293-392` —— 草稿工单 update 在事务内 `$locked->operations()->delete()` 全删重建工序行（:352）；对照**同文件 destroy 有**领料/退料/委外/成品入库四表引用检查（:407-414），update 一项都没有。
  3. **FK 口径为 RESTRICT**：`server/database/migrations/2026_08_14_110000_create_production_documents_tables.php:70` —— `operation_id ... restrictOnDelete`（对照 `operation_reports.operation_id` 为 cascade，:58，故报工记录不炸、只有委外单炸）。
- 触发路径（普通用户可达）：新建 DAG 工单（草稿，含 `is_outsourced=1` 的 PENDING 节点）→ 对该节点 `POST /production/outsourcings` 建草稿委外单（现有校验全部通过）→ 编辑工单改数量/计划日期/成品（PUT /production/orders/{id}，仍为草稿可改）→ DELETE work_order_operations 撞 FK RESTRICT → QueryException（update 仅 catch ProductionException；`bootstrap/app.php` 对 QueryException 无业务渲染）→ HTTP 500。
- 影响：无数据损坏（事务整体回滚），但该工单编辑路径 100% 失败且**无自愈**——每次编辑必 500，直到用户自行删除那张草稿委外单；违反宪法 §4.4.4（业务失败应转领域异常/统一响应）与 §4.3.3（守卫不全）。
- 建议修复方向：双管齐下——① 工单 update 删工序前比照 destroy 补 `OutsourcingOrder` 引用检查（归 1504 族业务码）；② 委外 store 补工单状态校验 `[RELEASED, PRODUCING]`（与 approve 同口径），从源头禁止对草稿工单建委外单。同步补 Feature 用例：草稿工单 + 草稿委外单 → 工单 update 应返回业务码而非 500。

#### B-2.【中】库存引擎数量运算全链路浮点：违反宪法 §4.1「数量 decimal(12,2) 同样经 bcmath 比较/累加」铁律（引擎核心，S2 分区 B-107 的控制器点位未覆盖此处）【核验:✅真实】

- 等级：中；分类：④ 不符合项目宪法（§4.1.1/§4.1.2 明文「任何写法均视为缺陷」）
- 引入：`57ad5bb`（库存引擎初建即浮点口径）；PR#33 组件口径新代码沿用该契约（`d7d3acb` 的 `OutsourcingController.php:399` 注释自认「引擎签名 quantity 为 float（历史契约单值传输……偏离记录⑤）」）。
- 证据（引擎核心三处 + 上游配合两处）：
  - `server/app/Services/InventoryService.php:48` —— `$quantity = (float) $m['quantity'];`
  - `:58` —— 出库充足性判断用浮点 `<` 直接比较：`(! $balance || (float) $balance->quantity < $quantity)`
  - `:91-95` —— 余额累加 `(float) $balance->quantity + $direction * $quantity` 后落库；`:104` 的 `balance_after` 审计快照同源浮点
  - 上游配合强转（PR#33 新增点位）：`OutsourcingController.php:399`（`(float) $item->required_qty`）、`:647`（`(float) $l['quantity']`）
- 影响分析：实际错账概率低——入参全部经正则限定 2 位小数、DB decimal(12,2) 每笔回写即舍入钳制（float64 对 1e10 级数量的绝对误差 ~1e-6，远小于 0.01 舍入粒度）。但该服务是**全系统唯一库存变动入口**（采购/销售/领退料/成品/委外发出/回收/余料退回/盘点九类流水全经此），宪法将数量浮点运算定义为缺陷级红线；S2 分区 B-107 收录的族 a/b 均为控制器层零值判断与盘点差异点位，引擎核心的比较/累加（本条）不在其列，两互补不重复。
- 建议修复方向：`apply/applyOne` 全链路字符串化（bccomp 判充足、bcadd/bcsub 累加，scale=2），上游调用方去掉 `(float)` 转换；盘点差异（S2 B-107 族 b）建议同波改 bcmath。改动集中单一服务 + 少量调用点签名。

#### B-3.【中】库存余额行加锁顺序全项目不统一 + 审核事务普遍无死锁重试：跨单据并发审核可 InnoDB 死锁，败方 500（S2 分区 B-108 的盘点子案为本条特例）【核验:✅真实】

- 等级：中；分类：④ 不符合项目宪法（§4.3.2「多资源加锁必须全项目锁序一致」）+ ① 运行错误（并发 500）
- 引入：`57ad5bb`（apply 无排序）；`d7d3acb` 在委外路径补了 material_id 升序预锁与 `, 2)` 重试（提交说明「补 DB::transaction 死锁重试」），其余模块未跟进——同一项目两套口径并存的现状本身即违反 §4.3.2。
- 证据（锁序事实与重试参数均为可验证代码事实）：
  - 根因：`server/app/Services/InventoryService.php:37-41` —— `apply()` 按调用方给定的 movement 顺序逐行 `lockForUpdate()`（:51-55），无 (product_id, warehouse_id, location_id) 规范化排序。
  - 三种调用风格并存：领料/销售出库单语句 `whereIn` 预锁（索引序，`PickListController.php:305-313`、`SalesOutboundController.php:358-366`）；委外发出/余料退回 `sortBy('material_id')` 升序（`OutsourcingController.php:380-384`、`:640`）；**采购入库/退料/盘点不排序**，按明细（用户输入）顺序逐行加锁（`PurchaseInboundController.php:365-380` movements 随 items 序、`ReturnListController.php:284-296`、`CheckController.php:280-287` 循环内逐行锁）。
  - 审核事务 attempts=1 全景：`PurchaseInboundController.php:341-416`、`SalesOutboundController.php:331`、`PickListController.php:281`、`ReturnListController.php:248`、`FinishedInboundController.php:259`、`CheckController.php:258-324` 均为裸 `DB::transaction(closure)`（无死锁重试）；仅建单路径与委外四处带 `, 2`（`OutsourcingController.php:169/421/564/698`）。
  - 项目自证：`OperationReportController.php:30-33` 注释明言「DB::transaction 默认不重试死锁败方（500），故必须全集升序单条获取」——报工路径已按此机理治理（b03b989「报工锁段改全量升序单锁消除死锁环」），库存行路径未做同等处理。
- 触发机制：如 PI-A 明细 [P1,P2] 与 PI-B（或退料单/盘点单）明细 [P2,P1] 并发审核同仓同位 → 两事务交叉持锁互等 → InnoDB 死锁检测回滚一方 → 1213 QueryException 冒泡 500（无重试）；未排序路径与索引序预锁路径并发同理可交叉。
- 影响与置信度说明：无数据损坏（败方整体回滚），用户侧表现为审核动作偶发 500、手动重试可成功；锁序不一致与 attempts 缺失为代码级确认事实，死锁发生为 InnoDB 标准行为 + 项目自身注释佐证（本地测试跑 SQLite 无法复现行锁语义，与 S2 B-108 的核验限制说明一致）。
- 建议修复方向：根修一处即可——`InventoryService::apply()` 入口对 movements 按 (product_id, warehouse_id, location_id) 升序排序后再逐行加锁（全项目库存行锁序随之统一并覆盖全部调用方，含 B-108 盘点子案）；备选为各审核事务统一补 attempts（治标：死锁仍发生但自动重试）。
