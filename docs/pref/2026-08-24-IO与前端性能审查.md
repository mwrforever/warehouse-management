## 三、确认优化区（编号 PF-1 起，本文件内唯一）

### PF-1【中】委外发出 approve：组件余额行循环内逐条锁查询——未沿用 08-16 P1-2 已落地的批量预锁模式（PR#33 新引入）【核验:✅真实】

- **位置**：`server/app/Http/Controllers/Api/OutsourcingController.php:380-405`（approve 事务内组件扣减段）
- **引入提交**：`d7d3acb`（PR#33）。旧版 approve 仅锁单个成品余额行（单条查询）；本次重构改为按组件扣减时，写成了循环逐条锁查询。
- **现状代码**：

```php
// OutsourcingController.php:379-405（现状：sortBy 后循环内每组件 1 条 lockForUpdate 查询）
$movements = [];
foreach ($locked->items->sortBy('material_id') as $item) {
    $balanceRow = InventoryBalance::where('product_id', $item->material_id)
        ->where('warehouse_id', $locked->warehouse_id)
        ->where('location_id', $locked->location_id)
        ->lockForUpdate()->first();
    // 该仓该位余额（bcmath 归一；无余额行=0——?? 对空左操作数短路，无需 nullsafe）
    $balance = bcadd((string) ($balanceRow->quantity ?? '0'), '0', 2);
    if (bccomp($balance, (string) $item->required_qty, 2) < 0) {
        throw new ProductionException(
            '商品['.($item->material->name ?? '#'.$item->material_id).']库存不足',
            1522
        );
    }
    ...
}
```

- **项目内既有惯例对照**（08-16 P1-2 已在四类单据审核落地批量预锁，含锁序论证注释）：

```php
// PickListController.php:295-313（已落地模式：余额行按唯一索引序一次锁定，循环内查 map）
// 循环前批量预锁（P1-2，宪法 §4.2.4 建议）：物料需求行/余额行按唯一索引序一次锁定，
// 循环内查 map——明细 N 行时查询次数从 ~2N 降为常数；批量锁按索引序获取与逐行等价，
// 且消除「两单明细顺序相反」时的交叉锁窗口（同索引序获取，无 ABBA 新方向）
$balanceMap = InventoryBalance::query()
    ->whereIn('product_id', $productIds)
    ->where('warehouse_id', $locked->warehouse_id)
    ->where('location_id', $locked->location_id)
    ->lockForUpdate()
    ->get()
    ->keyBy('product_id');
```

（`SalesOutboundController.php:353-360` 同款。）
- **方案**：对齐上述模式——`$locked->items->sortBy('material_id')` 先 `pluck('material_id')`，一条 `whereIn('product_id', ...)` + 固定 warehouse/location + `lockForUpdate()->get()->keyBy('product_id')` 批量预锁，循环内改查 map。
- **一致性/锁序分析**：`whereIn(product_id) + 等值 warehouse/location` 走 `balance_unique(product_id, warehouse_id, location_id)` 唯一索引，锁获取顺序 = 索引序 = product_id 升序，与现行 `sortBy('material_id')` 逐行升序**等价单调**，不改变「委外单 → 工单 → 组件余额行（material_id 升序）」锁序链条；批量获取还消除两单组件顺序相反时的交叉锁窗口（领料/出库控制器注释已论证，且有生产运行记录）。`apply()` 内余额行重复加锁幂等（引擎注释既有）。
- **预期收益**：组件 N 行时锁查询从 N 条降为 1 条（典型委外节点 2~5 组件 → 每次发出省 1~4 条查询）；事务持锁时长相应缩短，同仓并发发出/领料串行化窗口变小。收益定性为主，量级与 08-16 P1-2 同族。
- **风险**：低——与已落地的领料/退料/采购入库/销售出库四类审核完全同构，有先例测试模式可循（`PickListTest` 多明细批量锁用例）；SQLite（E2E）与 MySQL 行为一致。1522 消息含商品名逻辑不变（`items.material` 预载保留）。
- **置信度**：高（循环单查事实与批量预锁先例并存，直接可见）。

### PF-2【中】回收/退回「空串占位 + 流水单号回补 UPDATE」——全项目唯二例外，可重排语句顺序彻底消除（PR#33 新引入）【核验:✅真实】

- **位置**：`server/app/Http/Controllers/Api/OutsourcingController.php:491-525`（storeReceipt：apply → 取号建回收单 → 回补 UPDATE）、`:654-683`（storeReturn 同构）
- **引入提交**：`d7d3acb`（PR#33）。
- **现状代码**（storeReceipt，storeReturn :679-683 同构）：

```php
// OutsourcingController.php:491-525（现状：先写流水（source_no 空串占位），建单后再全表段 UPDATE 回补）
$this->inventoryService->apply([[... 'source_no' => '', ...]], auth()->id());   // :491-501
$receipt = $this->sequenceService->nextNoByConfig(                              // :503-519
    DocumentSequence::TYPE_OSR, fn (string $no) => OutsourcingReceipt::create([...]), ...);
// 流水单号回补（流水创建时回收单号未定，先以委外单号占位后回补——审计链完整）
DB::table('inventory_movements')
    ->where('source_type', 'outsourcing_in')
    ->where('source_id', $locked->id)
    ->where('source_no', '')
    ->update(['source_no' => $receipt->no]);                                     // :521-525
```

- **机理（两个成本点）**：
  1. **索引不匹配的 UPDATE 范围扫描**：`inventory_movements` 现有索引为 `movement_product_wh(product_id, warehouse_id)`、`movement_source_type(source_type)` 单列、`movement_created_at(created_at)`（`2026_08_12_090000_create_inventory_tables.php:41-42`）。回补 UPDATE 谓词 `(source_type, source_id, source_no)` 只能走 `movement_source_type` 单列索引，命中该类型**全部历史流水**后回表逐行过滤 `source_id`/`source_no`——扫描行数随委外回收/退回业务线性增长（每次回收扫全部 outsourcing_in 流水行，虽然真正要改的只有本事务刚插入的 1 行）。
  2. **并发事务间的锁竞争窗口**：两笔回收（或两笔退回）并发时，事务 A 未提交的 `source_no=''` 行落在事务 B 的 UPDATE 扫描范围内——InnoDB UPDATE 对扫描行加锁，B 会在 A 的插入行锁上阻塞等待（直至 A 提交/回滚）。非正确性问题（`DB::transaction(fn, 2)` 死锁重试兜底 + 最终 source_no 一致），但扩大了并发收发场景的锁等待面。
- **方案（推荐）：语句重排，先取号建单后 apply**——把 `nextNoByConfig`（创建回收单/退回单）挪到 `inventoryService->apply` 之前，流水 `source_no` 直接携带真实单号，**删除两处回补 UPDATE**。

```
重排后（storeReceipt）：锁委外单 → 锁工序全集 → 锁工单 → nextNoByConfig 建回收单（拿单号）
                      → apply(流水 source_no=回收单号) → 状态/推进 → 提交
```

- **一致性/锁序分析（重点）**：
  - 重排后与**全项目其它单据路径的顺序完全一致**：采购入库/领料/退料/销售出库/成品入库全部是「单据先建（store 时取号）→ approve 时 apply 流水带真实单号」，`source_no` 一次写对、无回补（对照证据：`PickListController.php:283→349`、`SalesOutboundController.php:333→410` 等，approve 段均无 movements UPDATE）。回收/退回是"创建即审核"才出现顺序纠结，重排是把例外拉回惯例。
  - `nextNoByConfig` 的契约是「须在调用方 DB::transaction 内调用」（`DocumentSequenceService.php:21` 注释）——重排后仍在 `storeReceipt`/`storeReturn` 的外层事务内，契约满足。
  - 锁序影响：`document_sequences` 行锁与 `outsourcing_receipts` 间隙锁从「余额行锁之后」提前到「之前」。全项目其余路径（如工单 store：锁成品 → 取号 → …）均为「单据/序列锁在前、余额行锁在后」的同向顺序；现行的「先 apply 后取号」反而是唯一反向样本。重排后跨路径单调性更强，无新增 ABBA 方向。
  - 死锁重试语义不变：外层 `DB::transaction(fn, 2)` 重跑闭包时已 apply 的流水随回滚撤销、重新写入，幂等性与现行等价。
  - 需同步更新两处注释口径（"先占号再补流水单号（先建单号引用唯一）"的说明将失效）。
- **预期收益**：每次回收/退回省 1 条 UPDATE（及其随业务增长的索引范围扫描 + 回表）；消除并发回收/退回事务在 movements 表上的相互锁等待窗口；审计链等价（流水最终 source_no 相同，E2E「按单号核对流水」断言不受影响——断言在事务提交后）。
- **备选方案（若重排被否）**：为 `inventory_movements` 增 `(source_type, source_id)` 复合索引（迁移），使回补 UPDATE 精确命中。可消扫描成本但不消锁竞争窗口，且引一条新索引（§6.3 需评审冗余性），劣于重排。
- **风险**：中低——事务内语句顺序调整，行为差异仅在「事务中途崩溃时流水短暂无单号」这一本就不可观测的窗口（回滚后无残留）；依赖 `OutsourcingDagTest`/`OutsourcingReturnTest`/`outsourcing.spec.ts` 既有断言（流水 source_no 最终值）作为等价性验证。
- **置信度**：高（UPDATE 谓词与索引的事实直接可见；全项目顺序对照穷尽 9 个单据控制器）。

### PF-3【低中】回收弹窗每次打开重复拉全量委外详情——所需三字段列表行全部已有（PR#33 新增）【核验:✅真实】

- **位置**：`web/src/views/production/OutsourcingsView.vue:396-413`（openReceipt）
- **现状代码**：

```ts
// OutsourcingsView.vue:396-413（现状：打开回收弹窗必拉一次完整 detail）
async function openReceipt(row: OutsourcingItem) {
  try {
    const d = await productionApi.outsourcingDetail(row.id)
    receiptId.value = row.id
    receiptRemaining.value = round2(Number(d.quantity) - Number(d.received_qty))
    receiptOutput.value = d.output_product_name ?? '—'
    Object.assign(receiptForm, { quantity: receiptRemaining.value, ... })
    ...
```

- **机理**：弹窗仅消费 `d.quantity / d.received_qty / d.output_product_name` 三字段，而委外列表 index 已全部返回（`OutsourcingController.php:90-95`：`output_product_name` join、`quantity`、`received_qty` withSum）。detail 是委外域最重的读路径（4 组关系预载 + `receivedQty` SUM 查询，`OutsourcingController.php:193/219`），每次打开回收弹窗白付一次。
- **方案**：`openReceipt` 直接用 `row.quantity / row.received_qty / row.output_product_name`，删除 `outsourcingDetail` 调用（编辑 `openEdit` 与退回 `openReturn` 确实需要 items 明细，不在此列）。
- **一致性分析**：列表行数据可能滞后（列表加载后他人已回收）——影响仅为「剩余可回收」预填值偏大，提交时后端 `storeReceipt` 事务内有权威超收校验 1524 兜底；且弹窗预填与列表展示同源（同为行数据）反而消除「列表显示 5 已收、弹窗显示 6 已收」的口径不一致。无缓存、无失效问题（每次列表加载即刷新）。
- **预期收益**：每次打开回收弹窗省 1 次重查询（≈5 条 SQL 的接口）；高频分批回收场景（一次委外多批回收，每批开一次弹窗）累积可观。
- **风险**：极低——纯前端取数来源替换；`received_qty` 列表口径（withSum '0.00'）与 detail 口径已在 PR#33 归一（bcmath 2 位），类型一致。
- **置信度**：高（字段供需关系直接可见）。

## 四、待裁决区（附源码佐证，不做「可实施」结论）

### PJ-1：工艺路线画布弹窗每次开窗重拉 4 个下拉请求（PR#32 新增）【核验:✅真实（现象，待裁决）】

- **现象**：`web/src/components/routing/RoutingCanvasDialog.vue:439-476`——弹窗每次打开（含编辑↔查看来回切换）都 `Promise.all` 重拉工序全量 + 三类商品各 per_page=100，共 4 请求。工艺路线管理为低频操作，但同一次会话内连续查看/编辑多张路线时重复拉取。
- **代码片段**：

```ts
// RoutingCanvasDialog.vue:452-457（每次开窗 4 请求并行拉全量下拉）
const [procs, fin, semi, raw] = await Promise.all([
  processApi.list(),
  productApi.list({ page: 1, per_page: 100, type: 'finished' }),
  productApi.list({ page: 1, per_page: 100, type: 'semi_finished' }),
  productApi.list({ page: 1, per_page: 100, type: 'raw_material' }),
])
```

- **方案 A（倾向维持）**：现状不动。理由：4 请求已并行（1×RTT）；主数据（工序/商品）可被其他用户新增修改，每次开窗取新鲜数据语义正确；低频管理操作，收益微小；会话守卫已防竞态。
- **方案 B（会话级缓存）**：模块级缓存 + 失效策略。**不推荐**：商品/工序的增改发生在别的页面（ProductsView/ProcessesView），跨页面失效需引入全局 store 或事件总线——为 4 个低频请求引入跨页状态同步，违反简单优先（宪法 1.1）；且缓存期内新增商品在下拉缺失，一致性无法低成本保证（按「无法保证一致性的一律不推荐」原则标注）。若商品规模逼近 100 条截断阈值（08-23 N-C 同族），届时应优先解决分页/搜索式下拉而非缓存。
- **利弊小结**：A 零成本零风险；B 省 4 请求/开窗但引入失效复杂度与新鲜度损失。**待用户裁决（建议 A）**。
