## 二、确认优化区

### P-1【中】委外发出（approve）扣减校验：循环内逐组件带锁点查余额行——08-16 P1-2 已批量化的同款旧模式在 PR#33 回归【核验:✅真实】

**位置**：`server/app/Http/Controllers/Api/OutsourcingController.php:380-405`（引入：`d7d3acb` PR#33）

```php
// :379-384（现状：逐组件 N 次带锁点查）
$movements = [];
foreach ($locked->items->sortBy('material_id') as $item) {
    $balanceRow = InventoryBalance::where('product_id', $item->material_id)
        ->where('warehouse_id', $locked->warehouse_id)
        ->where('location_id', $locked->location_id)
        ->lockForUpdate()->first();          // ← 每组件 1 次锁定查询，N 组件 N 次
    ...
}
// :407-409 随后 inventoryService->apply() 内 applyOne 对同一批余额行逐行再锁一遍（幂等重入）
if ($movements !== []) {
    $this->inventoryService->apply($movements, auth()->id());
}
```

**分析**：08-16 P1-2 已将领料/退料/采购入库/销售出库四类审核的"逐明细锁定查询"改造为 `whereIn` 批量预锁 + map 复用（宪法 §4.2.4【建议】的直接落地），并配批量锁回归测试；PR#33 的委外发出是新写的同构场景，但沿用逐行模式——组件 N 行即 N 次锁定往返，加上 `applyOne` 内引擎统一入口的重入锁，扣减段合计 ~2N 次余额行查询。委外组件数通常 1~5（节点输入材料数），属常数小 N，但与项目已确立模式不一致。

**优化方案**（与四类审核已落地实现同构）：

```php
// 循环前一次性批量预锁（余额行唯一索引 balance_unique(product_id, warehouse_id, location_id)）
$balances = InventoryBalance::where('warehouse_id', $locked->warehouse_id)
    ->where('location_id', $locked->location_id)
    ->whereIn('product_id', $locked->items->pluck('material_id')->unique()->values())
    ->lockForUpdate()->get()->keyBy('product_id');
foreach ($locked->items->sortBy('material_id') as $item) {
    $balanceRow = $balances->get($item->material_id);   // 内存取行，校验逻辑不变
    ...
}
```

**预期收益**：扣减校验段查询次数 N → 1；组件 5 行时该段从 5 次往返降为 1 次（apply 内重入锁为引擎契约，维持）。

**风险与一致性分析**：
- **锁序不变**：`whereIn` 批量锁在 `balance_unique` 唯一索引上按 product_id 升序获取，与现 `sortBy('material_id')` 逐行升序完全等价（08-16 P1-2 落地时同一论证已评审通过）；全局锁序「委外单 → 工单 → 余额行」不变量保持，无新 ABBA 方向。
- **行为等价**：无余额行返回 null → 余额 0 → 1522 拦截，语义与现逐行 `first()` 一致（whereIn 只是不返回缺行，map 取不到即 null）。
- 需同步回归 OutsourcingTest 1522 组件不足用例（行为不变应全绿）。

### P-2【中·随业务量确定性退化】回收/余料退回流水单号回补 UPDATE 仅命中 `source_type` 单列索引，需扫该类型分区全部行回表过滤【核验:✅真实】

**位置**：`server/app/Http/Controllers/Api/OutsourcingController.php:521-525`（storeReceipt）与 `:679-683`（storeReturn）（引入：`d7d3acb` PR#33）

```php
// :521-525（现状：回收流水回补；storeReturn :679-683 同款，source_type='outsourcing_return'）
DB::table('inventory_movements')
    ->where('source_type', 'outsourcing_in')
    ->where('source_id', $locked->id)
    ->where('source_no', '')
    ->update(['source_no' => $receipt->no]);
```

**分析**：`inventory_movements` 现有索引为 `movement_product_wh(product_id, warehouse_id)`、`movement_source_type(source_type)`、`movement_created_at(created_at)`（迁移 `2026_08_12_090000:41-42` + `103000`），**无 `source_id` 索引**。上述 UPDATE 优化器只能走 `movement_source_type` 单列索引 → 取得该类型下**全部流水行**的主键 → 逐行回表比对 `source_id`/`source_no`。执行成本随 `outsourcing_in` 类型流水总量线性增长：流水表只增不改不删（08-15 报告认定为全系统唯一无限增长表），每次回收（每次 1 条流水）都要全扫该类型已有分区——万级回收流水后每次回收变为万级行扫描的事务内操作。

**优化方案**（二选一，推荐 a）：

- **方案 a（推荐·代码层，零索引变更）**：`InventoryService::apply()` 收集并返回本批创建的流水主键（`applyOne` 内 `InventoryMovement::create` 返回的模型 id 已在内存，收集零成本），调用方改主键点查回补：

```php
// InventoryService::apply 签名 void → array（返回 int[]，既有调用方忽略返回值零影响）
$movementIds = $this->inventoryService->apply([...], auth()->id());
// 回补改主键 whereIn（点查，与行数无关）
DB::table('inventory_movements')->whereIn('id', $movementIds)->update(['source_no' => $receipt->no]);
```

- **方案 b（索引层）**：`movement_source_type(source_type)` 升级为 `(source_type, source_id)` 复合索引（替换旧单列索引避免冗余，宪法 §6.3；先例：08-15 P1-2a 的 `purchase_inbound_items` 复合索引替代单列）。UPDATE 变索引点查直达。`InventoryController::movements:84` 与 `ReportService:141` 的 `source_type` 单列筛选继续走新索引最左前缀，行为不变。

**预期收益**：回补 UPDATE 从「类型分区全扫 + 回表」降为主键/索引点查，消除随流水增长的事务内线性扫描；两处（回收+退回）同享。

**风险与一致性分析**：
- 方案 a：`apply` 返回值新增对既有 6 个调用方零影响（PHP 忽略返回值不改语义）；事务重跑（attempts=2 死锁重试）时重新 apply 重新收集，幂等；**顺带消除理论误伤面**——现状 `source_no=''` 条件若存在历史脏行（回补后理论不残留，但属防御面）会被误回补，主键回补语义精确到本批。
- 方案 b：替换索引需一次迁移（drop+add 同表），迁移期间无 DDL 锁外的业务影响（Laravel 迁移串行执行）；全项目经迁移演进（§6.1）合规。
- 两方案均不改锁序、不引入缓存、无跨存储一致性问题。

## 四、缓存机会评估（任务维度 2 专项）【核验:✅真实】

本轮范围内唯一讨论价值的两个候选，结论均为**不推荐引入**：

| 候选 | 读取频次 | 一致性维护评估 | 结论 |
|---|---|---|---|
| 工艺路线 DAG 图（`RoutingService::graph`，画布回显） | 路线列表/编辑时按需单条加载，低频 | 失效点多且分散：persist（新建/更新全量替换节点/材料/边）、toggle（启停）、delete 三个写路径都要失效；画布编辑要求「保存后立即回显最新」，任何失效遗漏直接导致编辑回显脏数据（用户可感知的正确性问题） | **不推荐**——单次 graph 约 11 条小表查询（头/product/nodes/materials/material/unit/process/outputProduct/edges/端点节点，全部小结果集），路线是低频主数据；与 08-15 §三.3「主数据缓存无需求」口径一致 |
